# 浏览器采集与平台扩展方案

本方案已替换旧 HTTP 榜单采集。默认范围为个护家清行业下全部三级分类：`category_scope.mode=all_level1`、`industry_id=5`，页面选择实时榜（`date_type=1`）；同时支持指定列表及不限定行业的全分类发现。指定列表存在任何无效行业归属或类目，或者限定行业没有可采集三级分类时，整任务在发现阶段失败。

适配器接口：`open_session` 管理登录与会话，`discover_scopes` 返回配置对应的通用分类快照，`collect_scope` 按页返回已校验记录、原始响应与安全业务参数，`close` 回收资源。共享编排只处理这些契约；罗盘页面流程、响应匹配、平台错误码和指标换算均在 `platforms/` 中实现。不要增加 YAML 页面流程引擎或动态插件加载。

配置分为全局运行参数、平台 Profile、任务范围和主任务发布设置。GUI 只读展示。未知适配器和配置错误在打开 Chrome 前拒绝。页面筛选顺序必须是分类确认后设置价格：真实罗盘切换分类会重置价格。自定义价格参数必须匹配 `10001-?`，禁止静默降级。单页结果会隐藏分页条，此时只允许请求/响应均为第一页。

页面请求在操作前登记，以 request 对象身份排除晚到旧响应，并校验完整业务参数的唯一值。中间请求、重复参数、错误日期、页码及筛选不能入库。上下文级监听覆盖新标签；回调缓存 response 对象，完成事件后再交付正文，不在回调内执行嵌套同步网络 API。

手动任务认证恢复限时 180 秒，定时任务直接结束并通知。恢复重建页面条件，逐页核对回到未完成页，不重写已有页。停止、跨天或恢复后契约不一致安全结束。超时重试有限且先恢复页面状态，禁止重复盲点。

新数据按平台和任务隔离。Alembic `0005_platform_capture` 升级前自动 SQLite backup，增加平台、任务配置快照、完整通用路径和安全业务元数据；旧请求范围未知，历史归属罗盘。原始响应和实际单位商品数据分开保存，金额单位 `CNY`、件数单位 `count`，只有罗盘解析器负责除以 100 和 10。历史原始材料路径不搬移。

网站每个平台/任务都有隔离索引，只有配置主任务更新现有根 `latest.json`。本次不增加平台切换 UI。通知、OSS、部署查询使用原有独立网络用途。

以下保留现有持久化、发布、调度与部署边界，采集部分以上述浏览器流程为准。

# 抖音电商罗盘榜单采集工程方案

## 1. 文档状态

- 工程：`douyin-compass-collector`
- 当前运行环境：本地 macOS
- Python：3.12
- 默认时区：`Asia/Shanghai`
- 默认任务：`compass_household_cleaning_realtime`

本文档只描述当前代码契约。仓库内自动化测试不代表真实账号、真实钉钉机器人、LaunchAgent 或另一台 Mac 已完成外部验收。

## 2. 目标与范围

工程使用每个平台独立 Chrome Profile 保存人工登录态，由 Playwright 操作真实 Chrome 页面，监听页面自身生成的结构化响应。正式榜单采集不提取 Cookie，不主动调用榜单 HTTP 接口。

当前业务范围通过任务 YAML 配置：

- 默认指定家庭环境清洁，全分类模式遍历所有非汇总一级分类；
- 每次任务保存当次分类树和执行范围快照；
- 根据当次响应校验指定列表或动态枚举全部三级分类；
- 排除名称为“全部”的节点；
- 忽略四级及更深节点；
- 每个三级分类采集商品实时榜完整 `total`；
- `page_size` 固定为 10，只递增 `page_no`；
- 任务、分类和分页全部串行，Playwright 对象只由创建线程操作；
- 分页可用时直接点击；检测不到分页才向上滚一次并重查，点击后核对请求、响应与可见活动页；
- 页面采集动作使用 0.5～1 秒随机间隔；
- 页面响应或操作超时最多额外恢复重试两次，按 1 秒、2 秒退避；
- 平台连续三次返回 `11001` 时停止本批，避免继续请求暂时不可用的服务；
- 本次只实现罗盘页面适配器，不增加多账号或多主机。

三级分类数量和每个分类的榜单条数都以当次接口响应为准，不写死分类个数，也不设置商品条数上限。

## 3. 主调用链

```text
读取并严格校验配置
→ 为每个任务建立 CollectionBatch、Manifest 和 batch_id
→ 启动独立持久化 Chrome Profile
→ 检查页面登录或验证状态，手动任务允许限时恢复
→ 通过显式注册表创建平台适配器与独立 Chrome 会话
→ 每个任务保存分类树及配置对应执行范围
→ 校验指定列表或按接口顺序枚举全分类
→ 为每个三级分类建立 category_run_id
→ 按任务配置串行采集分类，翻页滚动并匹配页面自身响应
→ 主线程按每个分类的页码顺序写入 raw gzip → SQLite raw 索引 → Manifest 镜像
→ 分类完整榜单校验
→ 正式发布或终结 dry-run 审计
→ 写入 JSONL 并发送一次钉钉批次汇总
→ 手动模式保留 Chrome；Scheduler 模式自动关闭
```

分类树由平台页面会话发现；每个任务保存自己的当次范围快照，不在每页重复请求。分类树完整响应会作为本机 raw 审计保存，但不会进入仓库 Fixture、普通日志或通知。

## 4. 请求契约

### 4.1 浏览器与认证

- 使用本机正式版 Google Chrome 和独立 `runtime/browser-profile/`；
- 不复用日常 Chrome Profile；
- 不提取 Cookie，不向共享编排传递认证资料；
- 平台签名和浏览器行为由页面自身处理；
- 从罗盘首页点击“查看同行榜单”进入新标签，再点击“商品榜单”；
- 分类确认后点击品牌与价格，最终以页面生成的完整业务请求校验条件。

### 4.2 分类树

分类接口：

```text
GET /compass_api/config_center/category/cate_list
```

分类参数由页面生成，适配器只监听该接口响应，不构造独立分类请求。

分类解析规则：

1. 按 `data.cate_list` 原始顺序遍历全部一级分类；
2. 一级分类 ID 重复或任意被消费层级结构不合法时立即失败并告警；
3. 对每个一级分类只枚举其直接三级分类；
4. 任意层级名称为“全部”的节点都排除；
5. 四级及更深节点不进入榜单采集队列；
6. 发现顺序跨一级分类连续写入 `discovery_order`，后续 SQLite、Manifest、GUI 和 CSV 都沿用该顺序；
7. 批次根字段保持为空，每个 `category_run` 保存真实一、二、三级分类快照。

### 4.3 商品实时榜

榜单接口：

```text
GET /compass_api/shop/product/product_rank/market_hot_sale
```

当前业务参数：

```text
page_no
page_size
industry_id
category_id
brand_type
price_bin
search_info
rank_data_type
begin_date
end_date
date_type
activity_id
```

`industry_id` 和 `category_id` 来自当次分类发现结果。`industry_id` 使用一级分类 ID；`category_id` 按页面级联选择器格式，将二级分类 ID 与三级分类 ID 使用英文逗号拼接。日期在任务开始时按北京时间计算一次，所有分类和分页复用同一个业务日期。

当前任务配置使用 `brand_type=-1` 不限制品牌，使用 `price_bin=不限` 不限制商品价格带。已验证的可选值包括 `brand_type=-1`、`brand_type=0`、`price_bin=不限` 和 `price_bin=10001-?`；其他品牌或价格带值在取得真实请求证据前不开放。实际请求值随批次写入 SQLite 和 Manifest，作为后续网站展示历史筛选条件的快照。

`_lid`、`verifyFp`、`fp`、`msToken`、`a_bogus`、`btm_*` 以及完整浏览器 cURL 不属于默认请求契约。若最小请求失效，只能基于新证据逐项增加必要字段。

## 5. 分页与分类完整性

第一页返回的 `data.page_result.total` 决定当前分类的完整页数：

```text
target_pages = max(1, ceil(total / 10))
```

- `total=0` 时仍只请求并校验第一页，且 `data_result` 必须为空；
- `total>0` 时完整请求全部页，不截断；
- 同一分类后续页的 `total` 必须与第一页一致；
- 非末页必须返回 10 条，末页条数必须与剩余数量一致；
- 响应页码、固定页大小、顶层状态和数据结构都必须通过契约校验；
- 完成后校验条数、商品 ID、排名唯一性以及排名连续性。

每一页只有在 raw gzip、SQLite 索引和 Manifest 三层都成功后，才计入已保存页。不同任务、批次或分类的分页不得拼接。

## 6. 分类失败处理

可跳过当前分类继续执行的“普通分类失败”仅包括：

- 网络请求错误；
- HTTP 响应错误；
- 已知响应契约错误。

处理规则：

- 每个普通分类失败都记录分类级日志和失败材料，并继续采集后续三级分类；
- `11001` 表示平台暂时不可用；连续三次出现时记录熔断事件并终止本批，`600003` 无权限不计入；
- 只要至少一个分类成功，正式模式发布成功分类并标记 `partial_success`；
- dry-run 在至少一个分类成功时终结为 `partial_success`，但不正式发布；
- 全部分类均为普通失败时，以 `failed` 收口，不生成正式商品记录或 CSV；
- 登录失效、中止、数据库、Manifest 或其他内部错误立即终止，不适用上述容错。

网络断连和临时网关错误在单次请求内最多额外重试两次；榜单是实时数据，普通失败页不会在后续运行中补拼。

## 7. SQLite 与状态模型

当前主要表：

- `collection_batches`：任务尝试、模式、统计、终态和发布边界；
- `category_runs`：动态三级分类快照、顺序、页数、条数和失败位置；
- `raw_responses`：分类分页 raw 路径和捕获时间；
- `product_rank_entries`：正式发布的成功分类商品榜单；
- `product_rank_entry_shops`：商品榜单记录与全部店铺的关系；
- `scheduler_checkpoints`：Scheduler 调和检查点。

日志、raw、Manifest、SQLite 和失败材料使用相同 `batch_id`。分类级材料再使用 `category_run_id` 定位，旧的单任务运行标识不属于当前模型。

### 7.1 正式模式

正式模式在发布事务中：

1. 校验 SQLite 中所有分类终态；
2. 为成功分类准备正式商品和店铺记录；
3. 准备完整 CSV 临时文件；
4. 将 CSV 原子替换到正式路径；
5. 提交 `success` 或 `partial_success`、版本、CSV 路径和 `published_at`；
6. 任一发布步骤失败时回滚数据库并补偿删除本次 CSV。

只有成功分类进入正式商品表和 CSV。失败分类仍保留审计状态和本机失败材料。

### 7.2 dry-run

dry-run 不是无状态模式。它保留：

- `collection_batches`；
- `category_runs`；
- `raw_responses`；
- 分类树和分页 gzip；
- Manifest；
- JSONL 和失败材料。

dry-run 不写正式商品和店铺记录，不生成 CSV，不分配版本，并保持 `csv_path=None`、`published_at=None`。因此 dry-run 的 `success` 或 `partial_success` 不能被当成正式发布，也不会阻止 Scheduler 后续正式执行同一计划。

### 7.3 正式发布唯一判据

`published_at IS NOT NULL` 是唯一正式发布判据：

- 包含正式 `success`；
- 包含正式 `partial_success`；
- 排除 dry-run；
- 排除仅进入 `publishing` 但尚未完成的事务；
- GUI 最近 CSV、幂等版本查询和运维判断都不得只看状态文本或文件是否存在。

## 9. CSV 契约

正式 CSV 使用 UTF-8 BOM，并固定为 8 列：

```text
分类
排名
商品缩略图
商品
店铺名称
用户支付金额
成交件数
首次上榜
```

规则：

- “分类”输出完整有序路径，罗盘当前为三级；
- 先按 `discovery_order`，再按分类内 `rank` 排序；
- 一个商品一行；
- 多店铺按接口顺序使用 ` | ` 拼接；
- 金额和成交件数只在展示层按平台单位换算；
- 文件按日期和 `task_id` 目录隔离；
- v1 不加版本后缀，后续强制版本使用 `_vN`；
- 通知只发送 CSV 文件名，不发送本机路径。

## 10. Scheduler

- APScheduler 在前台长期驻留，`launchd` 只负责用户级启动和异常拉起；
- 当前 cron 只接受每日固定时分；
- 同一平台、同一计划时间的多个任务合并为一个 Chrome 批次并严格串行；两平台独立调度及采集；
- 启动时根据 SQLite 检查点调和当日遗漏；
- 同日且在宽限期内补采，跨天或超过宽限记录 `missed`；
- Chrome/采集锁被占用时记录 `skipped_busy`，不排队；
- 任一非 dry-run 终态都会阻止同一计划自动重跑，包含正式 `partial_success`；
- dry-run 终态不占用正式计划；
- Scheduler 不等待人工输入，任务结束后自动关闭本次 Chrome；
- 重试策略与 Scheduler 规则仍列入后续重新梳理范围。

## 11. PySide6 GUI

`run` 默认打开 GUI，`--no-gui` 显式回退终端模式。GUI 当前支持：

- 正式模式、dry-run 和强制版本；
- 动态分类总数、分类路径、分类序号和分页进度；
- `partial_success` 与普通成功的不同结果文案；
- 安全 JSONL 事件展示和级别过滤；
- 协作式中止；
- 成功或失败后保留 Chrome，人工检查后再关闭；
- 启动和停止 GUI 自己拥有的 Scheduler；
- 对终端或 launchd Scheduler 只读展示，不越权终止；
- 打开本次或最近已发布 CSV；
- 打开输出目录；
- 在采集和 Scheduler 全部停止时清除本地采集数据。

清除操作只删除当前平台的批次及级联数据、CSV、raw、artifact 和网页暂存，保留数据库文件及归属元数据、另一平台、日志、Chrome Profile、锁、`.env`、配置和备份。当前不实现 macOS 系统通知。

## 12. 钉钉批次汇总

仓库根目录 `.env` 由程序主动加载，同名外部环境变量优先：

```dotenv
DINGTALK_ENABLED=true
DINGTALK_WEBHOOK_URL=<官方自定义机器人 Webhook>
DINGTALK_SECRET=<加签密钥>
```

行为边界：

- GUI、终端、强制模式、dry-run、Scheduler 和 missed 汇总都可发送；
- 每个批次只发送一次 Markdown；
- 不 @ 任何人；
- 使用 HMAC-SHA256 加签；
- 不跟随重定向、不自动重试；
- 只发送来源、模式、批次、时间、任务状态、页数、条数、CSV 文件名或安全错误分类；
- 不发送 Cookie、Token、本机绝对路径、响应正文或异常原文；
- 通知失败只写安全日志并更新 GUI 状态，不改变采集事务或退出码；
- 只有 `notify-test` 会以通知发送结果决定自己的退出码。

真实 Webhook 测试会产生外部消息，必须由人工明确执行 `make notify PLATFORM=tt`。

## 13. OSS CSV 上传与签名下载

OSS 默认关闭。开启 `OSS_ENABLED=true` 且所有配置校验通过时，单个任务的真实调用链为：SQLite 与 CSV 正式发布成功 → 上传 `runtime/exports/` 中的 CSV → 生成最长 7 天有效的私有 GET 签名链接 → 链接仅写入同批次钉钉 Markdown。

对象键为 `compass/<business_date>/<task_id>/<batch_id>/<中文 CSV 文件名>`，强制采集使用新的 `batch_id`，不会覆盖历史对象。RAM 专用用户只需目标 Bucket 的 `oss:PutObject` 与 `oss:GetObject`。

- dry-run、失败、中止与跳过任务不上传；
- OSS 上传处于发布边界之后，失败不回滚 SQLite、本地 CSV 或 `success`/`partial_success`；
- 失败只写 `oss_upload_failed` 等安全分类，钉钉保留 CSV 文件名并标记上传失败；
- 签名 URL 是短期 bearer 凭证，不进入 SQLite、Manifest、JSONL 或普通日志；
- 第一版不实现 OSS 自动重试或断电后的补传恢复。

```bash
make schedule PLATFORM=tt ACTION=uninstall
```

Make仅保留help、install、run、login、status、clean、schedule、notify、web、check；help/install之外必须指定`PLATFORM=tt|tb`。`make run PLATFORM=tt`与`make run PLATFORM=tb`统一默认`GUI=yes START=yes MODE=force NOTIFY=yes`，打开GUI立即创建新批次并通知；`START=no`打开空闲GUI，`GUI=no`回退终端。显式`normal`、`dry-run`模式从CLI传到GUI，不被强制新版本行为覆盖。`normal`保持已有发布结果则跳过，否则新批次完整重采，不实现补录。

登录、采集、状态和调度共用所选配置；GUI工作线程重新读取配置时继续过滤平台，GUI启动Scheduler也传递平台。平台清理持有所选平台的Scheduler及采集锁，只删除本平台独立数据库记录及文件，保留另一平台、共享历史日志、Profile和数据库文件。数据库元数据登记唯一平台归属，混库和跨平台复用拒绝启动。后台服务、GUI、采集锁、日志及控制文件均按平台隔离，两平台可以并行运行。通知与网页首屏使用所选平台，公开站默认抖音不变。

`make check PLATFORM=tt ACTION=test`运行完整后端测试；默认`ACTION=all`还运行前端测试及所选平台服务无副作用检查，不允许切换为安装或卸载。阶段测试文件仍保留在`tests/`供开发排查。

测试不启动真实 Chrome、不访问罗盘接口、不发送真实钉钉消息，也不注册 LaunchAgent。真实登录、真实采集、通知和系统守护必须单独人工验收。

## 15. 安全与保留

- Cookie 值、Webhook、签名密钥和完整请求头不得进入 Git、日志、Manifest 或通知；
- 原始响应默认保留 30 天；
- 失败材料和 JSONL 默认保留 10 天；
- SQLite 和正式 CSV 长期保留；
- Chrome Profile 含登录凭证，不普通复制、不提交 Git；
- `launchd` plist 不包含业务凭证；
- 本机备份不得上传公开网盘。
