# 淘宝平台开发执行方案

编制日期：2026-10-01。代码基线：`7d83091`。

本文是四阶段开发计划与编码代理执行说明，不是实现完成报告。用户授权代理自主选择常规实现方式、运行检查、修复问题并完成阶段验收，不再逐项确认这些取舍。本次整理方案不等于已经开发淘宝适配器。

## 1. 交付目标和已确定规则

最终交付包含淘宝本地采集、SQLite、原始响应与 Manifest、CSV、GUI、调度以及现有网站的平台切换。沿用现有项目，不创建第二套采集系统。

| 项目 | 实现规则 |
| --- | --- |
| 平台标识 | `taobao`，抖音继续使用 `compass` |
| 默认任务 | 建议 `taobao_household_cleaning_realtime` |
| 默认一级分类 | `50025705`，洗护清洁剂/卫生巾/纸/香薰 |
| 分类范围 | 每次任务从分类响应动态发现全部三级分类，保持源顺序，不采更深节点 |
| 统计时间 | 实时，`dateType=today`；任务开始按北京时间计算日期，不复制 PoC 日期 |
| 榜单类型 | 沿用已观察的交易总量，`rankType=gmv` |
| 其他筛选 | 全部店铺、价格不限、关键词为空；只支持已验证的条件 |
| 分页 | 20 条，每个任务初始化时设置一次；正常分类切换只确认、不重新设置 |
| 重建页面 | 新会话初始化时重新设置 20 条，避免刷新恢复成 10 条 |
| 更新时刻 | 不要求所有页的 `updateTime` 相同 |
| 任务时间 | 记录开始、结束；沿用现有技术审计时间，不新增逐页业务更新时间表 |
| 输出 | 分类路径、排名、商品缩略图、名称、跳转链接、店铺、支付买家数、访客数 |
| 数值 | 原文显示单值或区间，缺失显示 `-`；数据库保留空值，不能伪造为 0 |
| 串行执行 | 任务、分类、分页沿用现有串行编排 |
| 浏览器 | 淘宝独立持久化 Profile，建议 `runtime/taobao-browser-profile` |
| 采集方式 | 真实页面操作和响应监听；复用 `browser.py` 的会话机制 |

### 已自主确定的业务边界

1. 日期固定为任务开始的北京时间日期。跨午夜时结束本任务，未完成分类记录中断；已完整成功分类按现有部分成功规则处理，不把新日期数据写入旧批次。
2. 同一分类以第一页 `recordCount` 计算页数。若后续页总数变化、重复排名或排名不连续，该分类不能作为成功结果发布。允许不同页的更新时间；同一商品在分类内重复出现不算失败，按各排名位置保留所有记录，不去重。
3. 同一商品可以出现在不同分类；去重检查只在同一分类运行内进行。
4. 淘宝没有已验证的“首次上榜”字段。该字段保持不适用，网站隐藏此筛选，默认不筛首次上榜。
5. 指标筛选和排序沿用现有网站的区间下界语义，并清楚注明依据区间下界。缺失指标不参与启用后的数值筛选，指标排序时始终放到末尾，不能按 0 处理。
6. 网站首次进入默认抖音。切换平台重置筛选、排序、桌面分页和移动列表展示状态，不继承另一平台的指标条件。
7. 调度能力复用现有机制；建议淘宝任务沿用 14:00 的项目默认时间，由串行编排执行。真实验收前不为新任务安装服务或启动常驻调度。

## 2. PoC 证据与未验证内容

### 已观察到的接口契约

分类接口：`/mc/common/free/getCateInfo.json`。

- 成功响应是 `code=0`，`data` 为平铺数组，不是 `children` 树。
- 官方分类选择器脚本及真实响应共同确认前四列依次为 `parentId`、`cateId`、`cateName`、`cateFlag`。
- 层级通过父子关系计算；第四列不能当成层级。
- 后面的列未全部确认语义，第一版不依赖它们判断深度或叶节点。

实时排行接口：`/mc/mq/mkt/item/live/rank.json`。

- `dateType=today` 实际使用 `live` 路径。最初提供的 `offline` 路径属于另一统计模式，不能用它替代实时榜。
- 列表路径为 `data.data.data`，总数为 `data.data.recordCount`。
- `data.updateTime` 是页面数据更新时间；不同页可以不同。
- 排名来自 `cateRankId.value`。
- 商品来自 `item`：`itemId`、`pictUrl`、`title`、`detailUrl`。
- 店铺来自 `shop`：`title`、`shopUrl`、`userId` 等。
- 支付买家数来自 `payByrCnt.value`，访客数来自 `uv.value`。
- 指标可能是单值、区间、含“万”的区间或 `null`。
- `detailUrl` 包含淘宝或天猫的跳转地址，保持其原始跳转语义，将 `//` 补为 `https://`。
- 商品身份使用稳定的 `itemId`，不能使用会变化的跳转参数 `mi_id`。
- `shop.userId` 只确认是卖家用户标识，不能直接当作已验证的店铺 ID。
- 实际请求的 `cateFlag` 可能与地址栏不同，必须用当次分类元数据及实际请求核验。
- 排行响应未观察到明确页码字段，因此需要匹配请求身份、业务参数及活动页 DOM。

### 已观察到的页面行为

曾在水壶分类观察到 `recordCount=41`，20 条模式下各页为 20、20、1 条，排名范围为 1–20、21–40、41；该分类不属于本次目标一级分类，不能替代目标范围验收。

曾在目标范围内切换香薰用品、香薰蜡烛、香薰精油，正常切换保留每页 20 条。刷新页面会恢复成 10 条。页面有自动刷新请求，必须排除晚到响应和重复刷新响应。

2026-10-01 重新读取页面时，统计时间已进入新日期，地址栏仍保留 2026-09-30。实际日期以任务日期和观察到的业务请求验证，不能只看地址栏。

### 尚未完成的真实验收

- 默认一级分类的完整分类响应落盘和全部三级分类计数。
- 目标范围内两个三级分类的全部分页、商品 ID 去重和排名连续性验收。
- 淘宝在程序独立 Chrome Profile 中的登录与完整采集。
- 空榜、未知业务错误、登录过期和实际风控响应的完整契约。

Codex 内置浏览器曾能读取页面，但连接与网络监听多次超时。这是探索工具的观测结果，不能据此判定程序的 Playwright 适配器成功或失败。正式验收必须独立记录。

## 3. 当前代码链路与改动原则

当前链路为：

```text
CLI / GUI / Scheduler
→ AppConfig 严格验证
→ runner.create_adapter
→ PlatformAdapter.discover_scopes
→ 分类运行计划与范围快照
→ PlatformAdapter.collect_scope 返回 PageCapture
→ raw gzip → SQLite raw 索引 → Manifest
→ 分类完整性验证
→ SQLite 正式商品记录与 CSV 协调发布
→ OSS 公共快照与 latest 索引
→ 网站加载、筛选、桌面与移动展示
```

已有的可复用部分：`browser.py`、`platforms/contracts.py`、`runner.py`、`category_batch.py`、`category_collection.py`、调度、停止机制、锁、原始材料和平台隔离目录。

目前仍偏向抖音的部分：

- `config.py` 的任务业务类型直接引用 `platforms/compass_config.py`。
- `ProductRankEntry` 强制要求抖音金额、件数、首次上榜。
- 商品表这些列不可空，店铺表强制店铺 ID。
- `exporter.py` 固定八个抖音 CSV 列。
- `web_publisher.py` 只接受抖音 CSV 契约。
- 网站记录、排序、筛选及默认 `newOnly=true` 均针对抖音。

实施时保留旧抖音字段和历史读取兼容，只增加明确的淘宝字段及平台分支。第一版不增加动态插件、指标配置引擎、通用页面脚本 DSL 或另一个前端工程。新增变量、函数和状态必须有解释用途的注释。

## 4. 阶段一：固定接口契约与可重复验证

### 目标

让分类解析和商品解析先变成独立、可验证的纯函数；把未验证的平台行为留在浏览器适配器边界。

### 实施步骤

1. 重新检查当前分支和调用链，确认已有工作未被覆盖；运行现有自动化测试作为基线。
2. 新增 `platforms/taobao_config.py`，定义淘宝分类范围、实时日期、交易总量、20 条分页及已验证筛选条件。公共执行参数仍使用现有 `CollectionConfig`。
3. 新增 `platforms/taobao_categories.py`：严格验证顶层成功状态和数组格式，按前四列建立索引与父子关系，再从默认根只遍历到第三级。
4. 保持同父节点的源数组顺序，生成 `DiscoveredScope`；其元数据保存根、父分类、目标分类和实际 `cateFlag`，不要借用抖音的逗号分类 ID 格式。
5. 检查被消费分支的重复 ID、环、非法父子关系、空名称及无效根；无三级分类时报告范围错误，不能自动扩大到全部淘宝分类。
6. 新增 `platforms/taobao_product_rank.py`：验证实时响应嵌套结构、`recordCount`、列表、商品 ID、排名和指标；若两个来源都提供商品 ID，须检查一致性。
7. 指标解析同时保留原文与可选的规范化上下界。单值的上下界相等；`null` 不生成上下界；单位换算仅针对已验证的数值格式。
8. 定义实际请求的安全业务参数白名单：日期、分类、分页、榜单类型、价格、店铺类型、关键词、指标代码和版本。签名、认证、时间戳不进入摘要或配置。
9. 固定分页规则：`max(1, ceil(recordCount / 20))`；非末页 20 条，末页为剩余条数；0 条榜单只验证第一页。空榜规则先做明确的合成用例，真实验证另记状态。
10. 测试不同更新时间仍被接受；同一商品跨页重复必须通过并保留各排名；重复排名、断号、少页、多页、总数变化、错误日期、`offline` 请求、重复业务参数和值不匹配均不能通过。
11. 建立真实样本采集入口：通过页面操作和监听取得原始响应，保存在 `runtime/poc-taobao/`；仓库测试只使用人工构造或经过处理的小样本，标明来源，不把合成数据称为真实 PoC。

### 输出和验收

- 三个淘宝业务模块及聚焦测试，模块名称按现有目录模式组织。
- 分类清单包含完整三级路径与元数据，不写死分类数量。
- 原文区间、单值、“万”、空值、淘宝和天猫链接均有用例。
- 对抗用例能使验证失败，避免只测试“成功构造对象”。
- 现有抖音测试保持通过。
- 有真实材料时验证真实材料；没有时阶段报告写明“自动化通过、真实分类/分页验收待完成”。

### 给编码代理的执行指令

> 实现阶段一的淘宝配置、分类与排行解析，不改变现有抖音行为。先读当前契约，再写有失败能力的针对性测试。明确真实样本和合成样本。修复本阶段错误后运行聚焦测试与已有相关回归。尚未获取的真实数据保留待验收，不编造分类数量、错误码或商品数据。

## 5. 阶段二：打通一个三级分类的本地完整链路

### 目标

完成一个真实三级分类从页面采集到原始响应、数据库和 CSV 的闭环，同时兼容现有抖音数据。

### 实施步骤

1. 新增 `platforms/taobao.py`，实现已有 `PlatformAdapter`。使用独立 Profile，监听器在首次导航前安装，不依赖 Codex 内置浏览器。
2. 将 `TaskConfig` 改为按 `platform` 区分抖音与淘宝业务配置；公共字段保持统一。选择简单的显式联合与验证，保留现有抖音配置入口兼容。
3. 注册淘宝适配器，为 CLI、GUI、runner 返回正确的解析后任务配置；无效平台、混用字段、重复 Profile 在启动浏览器前拒绝。
4. 初始化页面并确认登录、实时、交易总量、默认筛选和 20 条。先安装监听，再触发页面动作；页面刷新后以新会话初始化恢复 20 条。
5. 完成一个分类的级联选择和第一页捕获，核验完整分类路径及实际业务参数。
6. 以请求对象身份和本次动作代次关联响应，等待 `requestfinished` 后读正文，排除旧请求、自动刷新和中间状态请求。
7. 第一页确定总数；按页点击并核验活动页。后续响应页码由请求确认，不推测响应含有页码；前三级图标排名以接口为准。
8. 扩展 `ProductRankEntry`：增加商品 URL、淘宝支付买家数和访客数的原文及可选上下界；抖音专属字段允许不适用，但抖音解析器仍严格要求其自身字段。
9. 扩展店铺公共字段，允许淘宝真实店铺 ID 未知，单独保存店铺 URL 与卖家用户标识。不得把卖家用户 ID 静默写成店铺 ID。
10. 新增 Alembic 迁移，沿用项目备份机制；保留历史字段与值，增加淘宝列并调整不适用字段的空值约束。只在临时数据库或备份副本先验证迁移。
11. 更新持久化写入与读取，让单值、区间、空值和商品 URL 来回读取一致；同一分类排名唯一约束继续成立；淘宝商品 ID 可重复，罗盘仍保留商品 ID 唯一约束。
12. 让 CSV 导出按平台选择固定契约。淘宝列为：分类、排名、商品缩略图、商品、商品链接、店铺名称、支付买家数、访客数。保持 UTF-8 BOM、源分类顺序和分类内排名顺序。
13. 继续使用现有 raw → SQLite → Manifest 的审计顺序，正式商品和 CSV 只在分类完整性通过后协调发布；失败分类不混入成功 CSV。
14. 增加配置与任务入口，用专门的样本配置验证一个分类；先 dry-run 验证原始采集，再验证本地正式落库和 CSV。真实外部上传使用隔离或关闭的验收配置，避免开发样本覆盖现有网站。

### 输出和验收

- 淘宝适配器、任务配置、迁移、模型、持久化及 CSV 改动。
- 一个分类所有页均已采集，条数与总数一致，允许同商品重复，排名为完整的 `1..N`。
- 保存实际请求摘要与响应，确认 `pageSize=20`、`dateType=today` 和当次业务日期。
- 数据库升级后的旧抖音记录、金额单位、件数单位和 CSV 内容不变。
- 空值从响应到数据库、CSV 始终未变成 0。
- CSV/事务失败时有补偿，失败结果不被标记成功。
- 自动化覆盖两平台的写入、读取、配置与导出；实际账号验证另列。

### 给编码代理的执行指令

> 在阶段一契约上实现阶段二：用真实页面监听完成单分类完整分页，扩展本地模型、迁移与平台 CSV。保留抖音兼容入口与行为。先验证迁移副本，再验证本地闭环，修复失败及补偿问题。每个真实结果保存本地证据；无法完成真实登录或接口捕获时，继续独立的数据库与导出工作，最后报告具体阻塞。

## 6. 阶段三：全分类任务、恢复机制、GUI 与调度

### 目标

将单分类能力接入已有任务编排，能够完整遍历默认范围，并明确处理失败、停止和跨天。

### 实施步骤

1. 每次任务只做一次分类发现，保存完整响应和目标范围；为每个三级分类分配现有 `category_run_id`，按发现顺序采集。
2. 任务开始初始化 20 条，切换分类后确认仍是 20 条。若同一会话意外丢失该设置，结束当前动作并通过明确恢复流程重建状态，不能把 10 条响应收作 20 条。
3. 复用全局停止、锁、日志和页面操作间隔。不要在 UI 线程运行采集，也不要跨线程复用 Playwright 对象。
4. 超时采用现有有限恢复次数。恢复前核对分类、筛选、20 条和已完成页；回到未完成页，不重新写入已经接受的页。
5. 若恢复所需的第一页总数与原采集不一致，分类失败，不能拼接两个不同状态的榜单。
6. 认证判断使用真实登录重定向、页面状态或已验证错误码。手动任务沿用限时人工恢复；定时任务记录失败并结束，不等待无人值守登录。
7. 淘宝错误码尚未完整验证，不复制抖音 `11001` 语义。未知响应保留证据并明确报错；同类平台错误连续三次时停止当前淘宝任务，避免对失效平台继续循环。
8. 检查动作前和响应接受后的业务日期；跨午夜沿用 `business_date_changed` 中断语义，不静默创建新日期任务，也不跨天补采实时榜。
9. 分类失败可沿用现有部分成功发布；全部失败不发布新快照。停止和认证失效后的未执行分类要有终态，不能遗留 `running`。
10. GUI 展示淘宝任务名称、平台、Profile、完整分类路径、当前分类/页码及最终成功失败数；复用现有任务选择、运行、停止和打开目录能力。
11. CLI 复用 `login --platform taobao` 和 `run --task taobao_household_cleaning_realtime` 等现有形式。完成适配后确认 help、status、dry-run 和 force 的行为一致。
12. 调度计划使用同一时区、宽限和串行队列。用测试时钟验证同日补采、跨天 missed、同任务版本和两平台任务锁；不为开发验收启动真实常驻服务。
13. 运行两个代表性三级分类的真实 PoC：优先从目标范围选择已观察的香薰蜡烛与香薰精油，以当次树核验 ID 和范围。完整采集全部页；若它们不能覆盖多页和尾页场景，在目标范围内补充合适分类。
14. 两个样本通过后再执行默认根的全分类任务，统计发现、成功、失败、未执行分类数和商品数，并记录任务开始/结束。

### 输出和验收

- 全分类任务可通过现有 GUI、CLI 和调度入口执行。
- 两个目标分类的所有页、稳定商品 ID、排名连续性、总数与 20 条保持均有真实证据。
- 控制页面测试覆盖旧响应晚到、自动刷新、分类切换、20 条丢失、超时、停止、认证失败、恢复和跨午夜。
- 只提交测试用例中的受控页面；真实认证材料和响应保存在 runtime。
- GUI 操作不阻塞，停止后所有相关运行状态完成收口。
- 自动化调度通过不等于已安装 LaunchAgent，也不等于真实定时任务已执行。

### 给编码代理的执行指令

> 完成阶段三的全分类运行和恢复，把淘宝接入已有 GUI、CLI 与调度，不复制第二套编排。重点验证异步旧响应、20 条保持、总数漂移、停止与跨天。先运行目标范围两个分类的全部分页验收，再运行全范围。修复可重现的问题，按完整成功、部分成功、失败和中断分别记录结果，不隐藏失败分类。

## 7. 阶段四：网站快照、平台切换与淘宝指标展示

### 目标

让现有桌面和移动网站能够切换抖音、淘宝，正确展示各平台的指标和商品链接。

### 实施步骤

1. 保留当前单一前端工程、OSS 公共数据和不可变快照发布方式，继续使用现有 `platform/task` 隔离索引。
2. 为 `web_publisher.py` 增加淘宝 CSV 解析分支，严格核验各平台列名，不把淘宝指标写进抖音金额或件数字段。
3. 为新快照增加明确版本及平台、任务、任务开始/结束时间；前端兼容已有抖音旧快照。失败任务不覆盖此前有效索引。
4. 淘宝发布到自己的 `taobao/<task>/latest.json`。原 `web_primary_task_id` 继续控制旧根索引归属，淘宝不自动覆盖抖音旧根。
5. 保持“不可变 data/CSV 上传完成后，最后更新 latest”顺序，验证上传失败时旧索引仍可读取。
6. 数据源采用简单明确的两个平台配置：原 `VITE_DATA_INDEX_URL` 保持抖音兼容，增加淘宝公共索引配置。第一版不引入平台目录服务。
7. 前端定义按平台区分的记录类型或显式平台字段，淘宝使用自己的两项指标和商品链接；旧抖音记录仍按原契约读取。
8. 在桌面与移动主界面提供抖音/淘宝切换。切换控件要在加载、错误和空数据状态下仍然可用。
9. 加载新平台时清空旧展示状态、重置 loading/error，取消或忽略旧平台的异步结果。核对索引与快照的 platform、task、batch 一致，防止配置串用。
10. 切换平台重置关键词、分类、指标筛选、排序、分页及移动端展开状态。淘宝默认 `newOnly=false`，隐藏首次上榜筛选及标记。
11. 桌面表格与移动卡片按平台展示：抖音为原指标；淘宝为支付买家数、访客数。区间按原文显示，缺失显示 `-`，缩略图缺失保留现有占位行为。
12. 商品名称链接使用响应提供的地址；仅允许已验证的正常 HTTP/HTTPS 商品跳转 URL，使用新窗口并补充正常外链属性。不要根据 `itemId` 猜测替代链接。
13. 淘宝数值筛选和排序使用已解析的可空下界或明确解析结果。修复现有“解析失败返回 0”对淘宝的错误语义，不改变旧抖音有效数值的比较结果。
14. 按当前包管理方式增加最小必要的前端逻辑/状态测试；不只依赖 TypeScript 构建。覆盖首次上榜默认值、空指标、区间下界、平台切换和晚到请求。
15. 对桌面、移动端的正常数据、空数据、未配置淘宝数据源和加载失败做本地浏览器验收，保存截图与简短结果。
16. 构建通过后生成可审查的发布材料。真实上传与部署只使用项目已有且已授权的目标；配置或访问缺失时保留本地构建与证据，并把线上验收标为待完成。

### 输出和验收

- 两个平台的独立 CSV、data 和 latest 契约。
- 桌面和移动端可切换，默认条件和数据相互独立。
- 切换到淘宝不会因为默认“仅首次上榜”而产生假空列表。
- `null` 既不是 0，也不会在数值筛选中被误认为真实值。
- 商品缩略图、名称、店铺、指标、跳转和任务时间均可对照本地快照核验。
- 两个平台请求竞争时，晚到响应不能覆盖当前平台。
- 旧抖音索引和数据继续可用；平台发布不会互相覆盖。
- 前端测试、类型检查和生产构建通过；本地视觉验收和线上验收分别记录。

### 给编码代理的执行指令

> 完成阶段四的淘宝网站契约与平台切换，复用现有网站。先打通快照生成，再做加载状态、独立筛选、桌面和移动展示。用对抗用例验证首次上榜默认值、空值和异步结果串用。运行前端测试和 build，完成本地浏览器验收并保存证据；按既有目标准备发布，外部访问不足时不要把本地验收称为上线成功。
