# 备份与恢复

当前只支持 PostgreSQL，连接与迁移入口见 [PostgreSQL 本地运行与 RDS 接入](PostgreSQL迁移与运行.md)。抖音与淘宝分别备份各自数据库，恢复时必须匹配 `runtime_platform` 登记的平台归属。

## 1. 备份范围

- PostgreSQL 数据库：批次、分类执行、raw 索引、正式排名、店铺快照和 Scheduler 检查点。
- `runtime/exports/<platform>/<YYYY-MM-DD>/<task_id>/`：正式 CSV。
- `runtime/raw/<platform>/<YYYY-MM-DD>/<task_id>/<batch_id>/`：分类树、分页原始响应与 Manifest。
- `runtime/artifacts/<platform>/<YYYY-MM-DD>/<task_id>/<batch_id>/`：对应失败材料。
- `runtime/web-publication/<platform>/<task_id>/<batch_id>/`：本地网站快照；按需要备份对应平台日志。

数据库备份不包含这些本地文件，应按同一批次一起保存，保持原路径层级。不要把 Cookie、`.env`、浏览器 Profile 或数据库凭证上传到公共存储。不要迁移旧 Chrome Profile，换机器时重新登录两平台。

## 2. 一致性与恢复

先停止 Scheduler 与采集，确认没有写入。数据库使用 `pg_dump --format=custom` 备份，恢复使用 `pg_restore`；凭证通过安全环境或 PostgreSQL 密码文件提供，不写入命令行或仓库。RDS 可使用服务端备份。

1. 在目标独立数据库恢复备份，避免覆盖仍需保留的数据。
2. 按原层级恢复对应 CSV、raw、Manifest、失败材料与网站快照。
3. 将该平台的数据库连接环境变量指向恢复后的数据库。
4. 执行 `make status PLATFORM=tt` 或 `make status PLATFORM=tb`，核对平台归属、批次和发布状态。
5. 核对正式记录数量、`published_at`、CSV 路径和文件内容；必要时进行独立 dry-run 验证，再恢复 Scheduler。

CLI 启动时执行当前 Alembic 升级。升级前另行备份，不手工修改 `alembic_version` 或发布标记。

## 3. 发布判据

`published_at IS NOT NULL` 是正式发布唯一判据：

- 正式 `success` 和 `partial_success` 应同时具有版本与 CSV。
- dry-run 即使成功，也不写正式商品、店铺、发布版本或 CSV。
- 仅存在 CSV 不能证明正式发布；数据库已发布而 CSV 丢失时，应恢复原文件。
- `publication_unconfirmed` 表示提交结果未知，先核对原批次，不能直接重跑或伪造终态。

## 4. 清理原则

按平台、业务日期、批次身份核对后再清理，不能只按文件修改时间判断数据归属。保留一批已发布结果时，同时保留其数据库记录及上述关联材料；批次内的失败分类材料仍属于该批次审计记录。

`make clean PLATFORM=tt ACTION=data` 或 `make clean PLATFORM=tb ACTION=data` 会清空所选平台的数据，不提供“只保留某天”的功能。一次性的历史整理不改变 YAML 的日常保留策略，也不删除远端 OSS 快照。
